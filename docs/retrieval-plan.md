# Retrieval improvements: what to take from Grok, what to refuse

Compiled from two investigations: how Grok's DeepSearch actually works, and whether
LangGraph belongs in the request pipeline.

**Thesis.** Grok's *retrieval* is better than ours. Grok's *citation discipline* is
catastrophically worse — 94% failure on citation attribution, fabricated URLs in more
than half of cases (Tow Center, Columbia; 1,600 queries). The work is to import the
first without importing the second. LangGraph is the wrong vehicle for our pipeline,
but it was right about one thing, and that thing is worth building.

Every change below is bounded by one rule: **a retry changes what we search for, never
what counts as evidence.**

---

## 1. Carry `search_phrases` into the domain — the enabling step

`search_phrases` is generated by the extractor and **dropped at the extraction
boundary**. It exists only in `app/extraction/llm.py` (the internal model, and the
response schema we send to Gemini). It never reaches `app/domain/claim.py`, so
resolvers physically cannot see it — `candidates(claim)` receives a `Claim` with no
such field.

We pay Gemini to decompose every claim into query phrasings, and throw the result away.

- Add `search_phrases: list[str]` to `Claim`
- Plumb it through the extraction → domain mapping

Behaviour change: none. This is scaffolding for §2.

## 2. Bounded iterative retrieval — Grok's real advantage

`_run_resolver` runs `candidates → snapshot → relate` **once**, on the claim text.
Nothing found → abstain. Grok re-queries and refines up to 10 steps.

Wrap `_run_resolver` in a retry that re-queries with the next `search_phrase` when
evidence came back empty.

Bounds are the design, not decoration:

| Bound | Why |
|---|---|
| Max 3 attempts per resolver | We have an 8s budget (`TARGET_SECONDS`); Grok has minutes |
| Deadline-checked before each retry | A retry that blows the budget is worse than an abstention |
| Retry only on **empty** evidence | Weak evidence is an answer. Retrying past it is shopping for a better one |
| Wrapper around the resolver | `SourceResolver` protocol stays untouched |

**Cost: no Gemini quota.** Extraction runs once per submission, upstream of
`_resolve_claim`. `relate()` carries no model call. Retries spend DB queries, fetches,
and local ONNX embeddings — all free. This matters while the free tier is the ceiling.

**What does not move:** `snapshot_id` stays required, `citation_url` still comes from
`snapshot.final_url`, `locate_excerpt` still yields `INSUFFICIENT` when the phrase is
absent from fetched text.

## 3. Deterministic sufficiency gate — Grok's scratchpad, minus the model

Grok summarises into a scratchpad and asks itself whether it has enough. That
self-assessment is the vector that produces its failure rate.

Ours is a rule, not a judgement:

    continue iff  evidence is empty
              and attempts remain
              and the deadline allows
              and an unused, distinct phrase exists

No model call. Nothing to persuade. We explicitly refuse "ask the model whether it is
satisfied" — that is the single most tempting idea in the Grok architecture and the
one that breaks ours.

## 4. Observable retrieval — what LangGraph was right about

LangGraph's genuine insight is that reasoning should be visible. We don't need the
framework for it: the pipeline already carries the seams (`SkippedCheck`, resolver
names, per-attempt outcomes). Stream them over SSE.

This is the highest **demo** value in the document. Our abstention rate is high, and an
abstention with no visible reasoning looks like a broken system. The same abstention
showing

    corpus       — 3 phrasings, 0 matches
    fact-checks  — 0 matches
    verdict      — UNVERIFIED: no citable source exists

looks like a system with integrity. Identical behaviour, opposite impression. This is
what converts our most conspicuous weakness into the thing that distinguishes us.

## 5. Recency fallback — the honest structural gap (optional)

Grok's edge we cannot match is the live X firehose. Our corpus is batch-ingested, so a
claim about something three hours old finds nothing and we abstain: correct, but
useless to the person asking.

A live-fetch resolver that fires **last**, only when every corpus resolver returned
empty. Still `SecureFetcher`, still snapshotted, still excerpt-located, still tiered.

Optional because it is the most work and the most risk this close to demo day.

---

## What we refuse, and why

| Refused | Reason |
|---|---|
| LangGraph in the request pipeline | M40's fixed order (cache probe before governor, governor before any provider call) is asserted by tests against our own call sequence. Graph edges are rewireable by accident. Plus a dependency tree on a 2 GiB container already paying a ~6s cold start. |
| Model-chosen retrieval strategy | A model steering retrieval is a model with indirect influence over the verdict. That is precisely Grok's failure vector. |
| Model-generated citations | The extraction schema has no URL field. Not an oversight — the guarantee. |

LangGraph is worth reopening if we ever want streamed reasoning as a *presentation*
layer over a pipeline that stays deterministic underneath. Not before.

---

## Acceptance test

The audit harness already measures both numbers. The change succeeds iff:

- **Abstention rate falls** — retrieval found things it had been missing
- **False-positive rate does not move** — we found more; we did not lower the bar

If abstention falls *and* false positives rise, the retry loop lowered the bar and the
change must be reverted. Measurable pass/fail, not a judgement call.

**Blocker:** the audit has never produced a clean run (Gemini quota). A clean baseline
must exist *before* §2 lands, or there is nothing to compare against.
